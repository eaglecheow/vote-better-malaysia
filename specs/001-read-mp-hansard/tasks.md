## Format: `[ID] [P?] [Story] Description`

- Every executable task uses `- [ ] Tnnn`, an optional `[P]`, a story label within story phases, and exact repository-relative file paths.
- `[P]` means different writable files and no unmet dependency once the task's stated prerequisites and the phase gates have passed. It never permits implementation before RED. Test-writing tasks may overlap; their RED verification and shared-module edits remain ordered.
- Every task includes its observable completion check. A test-writing task stays unchecked until its linked RED-verification task confirms the required behavioral assertion failures.

## Path Conventions and Execution Rules

Use the single-project layout in `plan.md`: `src/`, `worker/`, `scripts/`, `public/`, `tests/unit/`, `tests/browser/`, `tests/fixtures/`, `docs/`, and `.github/workflows/`. Evidence belongs to `specs/001-read-mp-hansard/evidence/` and is created only when checks actually run.

For every RED gate, run the named test files through `npm test -- --run <paths>` and record requirement/test identifiers, exact command, revision or working-tree fingerprint, expected failure, observed initial assertion failure, and relevant output in `specs/001-read-mp-hansard/evidence/tdd.md`. Repair import, syntax, dependency, fixture, and harness errors first; they and already-passing assertions do not count as RED. Minimal nonfunctional entry-point scaffolding is allowed solely to make assertions executable; it must not implement the tested behavior. Each covered behavior needs its own observed failure before implementation, even within a grouped task.

GREEN tasks run the affected files, the existing regression suite, and `npm run typecheck`, then record passes and necessary refactoring or an explicit no-refactor decision. If refactoring changes behavior or a defect is found, first add and verify a failing regression assertion. Never invent evidence or mark a blocked acceptance task complete.

Every introduced or changed function/method, including scripts, worker code, tests, callbacks, and test helpers, requires accurate JSDoc/TSDoc explaining purpose, parameters, returns, and relevant side effects/errors. This applies to every code task, not only the tasks explicitly repeating it. Keep authoritative source/result/freshness rules in `src/source.ts` and bilingual messages in `src/messages.ts`; no duplicate filtering, inferred identity, backend, proxy, framework, or archive truncation.

The commands named below are implementation deliverables from `quickstart.md`; their presence here does not mean they currently exist. Physical devices, stable browsers, human usability participants, repository administration, and publication access are delivery prerequisites. Missing access/evidence blocks the affected delivery task, rather than allowing an emulated result or local workflow file to stand in for it.
